Ride Logging & Live Ride HUD

Transform MotoVault from "open when something breaks" into "open every time you ride" — with a real-time dashboard showing speed, lean angle, altitude, and route on a live map.

1. Problem Statement

Motorcycle riders use REVER (millions of downloads), Calimoto, and Scenic as daily ride-tracking companions — apps they open every time they ride. MotoVault, by contrast, is opened only when something needs attention: a diagnostic, a maintenance task, or an expense to log. The current DAU/MAU ratio is estimated at ~10%, a pattern typical of utility-only apps. Without a daily engagement touchpoint, MotoVault cannot build the habitual usage necessary for long-term retention or sustainable subscription revenue.

Who experiences this: Every active MotoVault user who rides regularly (estimated 70%+ of user base, riding 2–5 times per week in season). These riders currently have no reason to open MotoVault on a ride day — only when something needs logging or fixing.

Cost of not solving it:

From a competitive standpoint, REVER and Calimoto own the "daily ride" moment. Every ride logged in REVER is a ride NOT logged in MotoVault — and when a rider needs diagnostics or maintenance tracking, they'll consider the app they already have open. From a data accuracy perspective, MotoVault's maintenance schedules depend on accurate mileage, but motorcycle.current_mileage is only updated when users manually edit their bike. Ride logging would auto-increment mileage, making OEM task thresholds and cost-per-mile calculations significantly more accurate. From a revenue perspective, ride logging is the highest-frequency Pro feature possible — gating ride history and detailed analytics behind Pro creates a daily reminder of the subscription's value.

MotoVault's unique advantage: No ride-tracking app auto-updates a bike's service mileage or triggers maintenance reminders based on ride distance. REVER tracks rides. MotoVault can track rides AND tell you "you're 200 miles from your next oil change" when you finish. The live Ride HUD — showing speed, lean angle, altitude, and route on a real-time map — makes MotoVault the app riders WANT to have running, not just the one they open after the fact.

2. Goals

  • User Goal
    Record every ride with zero friction. Starting a ride takes one tap from the home screen. Ending a ride presents instant stats (distance, duration, avg speed) and a mileage update prompt. Target: ride start-to-recording in under 3 seconds. Measured by: time from "Start Ride" tap to first GPS fix recorded.
  • User Goal
    Experience a rich, real-time Ride HUD. While riding, the user sees a live map with their route, current speed (large, glanceable), lean angle gauge, altitude, and ride stats — all on a dark, high-contrast screen optimized for outdoor visibility. Measured by: % of rides where the HUD screen is visible for >50% of ride duration (indicates active engagement vs. pocket-riding).
  • User Goal
    Keep maintenance schedules accurate without manual effort. Ride distance is added to the bike's odometer after each ride. Maintenance tasks with target_mileage are automatically rechecked. Measured by: % of rides that result in accepted mileage updates (target: 85%).
  • Business Goal
    Increase DAU/MAU from ~10% to 25%+. Ride logging creates a reason to open MotoVault on every ride. Measured by: DAU/MAU ratio, 90 days post-launch.
  • Business Goal
    Grow Pro subscriptions through high-frequency feature gating. Free tier: 5 rides/month with basic stats. Pro: unlimited rides, full history, lean angle analytics, route maps. Measured by: incremental Free→Pro conversion attributed to ride-related upgrade prompts.

3. Non-Goals

Turn-by-turn navigation.
Navigation is Calimoto's and REVER Pro's core offering, requiring deep map engine integration, voice guidance, and offline routing. This is a separate product initiative. MotoVault records rides — it doesn't plan them.
Community route discovery or social feed.
Sharing and discovering routes requires a community layer, moderation, and network effects that take months to build. P2 consideration: design the rides table to support public visibility flags for future sharing, but don't build the community UI in v1.
Crash detection and automatic emergency calls.
Automatic crash detection requires accelerometer analysis, false-positive handling, and potentially emergency service integration (911 calling). This carries legal liability and needs dedicated safety engineering. Out of scope for v1.
Safety contact / emergency SMS notifications.
Live location sharing with a safety contact requires backend SMS infrastructure (Twilio/SNS), ongoing per-message costs, and legal liability considerations. Descoped from v1 — may revisit as a future Pro feature once ride logging adoption is validated.
Group ride coordination or multi-rider tracking.
Real-time multi-user location sharing requires a fundamentally different backend (presence channels, conflict resolution, privacy controls). Out of scope for v1.

4. User Stories

Core: Ride Recording

As a recreational rider, I want to tap one button to start recording my ride so that I can track distance and duration without fiddling with settings.

Edge: If no motorcycle is selected (no bikes in garage), prompt to add a bike or select "Quick Ride" without a bike association.

As a rider mid-ride, I want the app to continue recording my GPS track even when the screen is off or I switch to another app so that I get a complete route without keeping MotoVault in the foreground.

Edge: Battery saver mode may throttle GPS. Show a warning if low-power mode is detected: "Location accuracy may be reduced."

As a rider finishing a ride, I want to see an instant summary (distance, duration, avg speed, max speed, elevation gain) and be prompted to update my bike's mileage so that my maintenance schedule stays accurate.

Edge: If GPS accuracy was poor (>50% of waypoints with accuracy >100m), show a warning: "GPS quality was low — distance may be inaccurate. Adjust mileage manually if needed." Present the suggested mileage as editable, not auto-committed.

As a touring rider on a multi-day trip, I want to pause and resume a ride (e.g., at a fuel stop or overnight) so that rest periods don't count toward ride duration and I can keep one continuous trip log.

Edge: If the app is force-killed during a paused ride, the ride should be recoverable on next app open. Store ride state in expo-secure-store.

Core: Live Ride HUD

As a rider with a phone mounted on handlebars, I want to see a dark, high-contrast Ride HUD with my current speed displayed large enough to read at a glance so that I can monitor my pace without taking my eyes off the road for more than a split second.

Edge: Speed must be readable in direct sunlight. Use maximum brightness prompt when ride starts. White-on-black text, minimum 72px font size for the speed number.

As a sport/canyon rider, I want to see my current lean angle displayed as a gauge so that I can track how aggressively I'm cornering and improve my riding technique over time.

Edge: Lean angle is derived from the device gyroscope and requires the phone to be mounted rigidly. Show a one-time calibration prompt: "Mount your phone and tap Calibrate to set the zero position." If no gyroscope is available, hide the lean gauge and show altitude instead.

As a touring rider, I want to see my route drawn on a live map in real time so that I can see where I've been and orient myself geographically.

Edge: Map should auto-pan to keep the current position centered. Show a gradient polyline (start → current) with the route color transitioning from blue to green. If GPS signal is lost for >30 seconds, show a "GPS signal lost" indicator on the map.

As a mountain/ADV rider, I want to see my current altitude and elevation changes so that I can track how much climbing I've done on a ride.

Edge: GPS altitude can be inaccurate (±30m). Display altitude as an integer (no decimals) and use barometric altitude from the device if available for better accuracy.

As a rider reviewing stats mid-ride, I want to see secondary stats (distance, avg speed, max speed, elevation gain) in a compact row below the primary metrics so that I get a complete picture without scrolling.

Core: Mileage Sync

As a maintenance-conscious rider, I want my ride distance to be automatically suggested as a mileage update for my motorcycle so that my OEM maintenance schedules stay accurate without manual editing.

Edge: Display as "Add X mi to odometer? (Current: Y mi → New: Z mi)" — never auto-commit. Rider can accept, edit, or skip. If skipped, ride still saves but mileage doesn't update.

As a rider who just hit a maintenance milestone, I want to see a notification after my ride saying "Oil change due — you've passed 6,000 miles" so that I act on maintenance tasks at the right time.

Edge: Only show for tasks with target_mileage that the new odometer reading exceeds. Don't show for tasks already completed or skipped.

Edge Cases & Empty States

As a new user who hasn't added a bike yet, I want to be able to start a "Quick Ride" (unassociated with a motorcycle) so that I can try ride logging immediately and associate the ride with a bike later.

As a rider in an area with poor cell service, I want ride recording to work fully offline (GPS only, no network required) and sync data when connectivity returns so that backcountry rides are fully tracked.

Edge: Safety contact notifications require network. If offline when safety timeout triggers, queue the alert and send immediately when network is restored. Show rider a warning: "No network — safety alert will send when connected."

As a Free tier user, I want to see how many of my 5 monthly rides I've used, and when I hit the limit, a clear upgrade prompt rather than a silent failure.

P2 Future Considerations

FeatureDesign Consideration for v1
Route Sharing & Discovery Add is_public BOOLEAN DEFAULT false and region TEXT to the rides table. Do not build the sharing UI, but design the schema to support it. Users could eventually browse public rides by region.
Ride-Linked Weather Data Store weather_snapshot JSONB on the rides table for start/end conditions. Enables future analytics ("Your average speed drops 10% in rain"). Don't fetch weather data in v1, but reserve the column.
Safety Contact & Emergency SMS Designate a safety contact who receives SMS on ride start/end and inactivity alerts. Requires Twilio/SNS backend, per-message costs, and liability review. Descoped from v1 — revisit once ride logging adoption is validated. Design the rides table to include safety_enabled BOOLEAN for future activation.
Live Location Sharing Link Extend the share link system to support real-time ride tracking (a live URL a contact can open to see the rider's position updating). Requires WebSocket or Supabase Realtime. Out of scope for v1.
Ride Insights (AI) "You ride 30% faster on weekends" or "Your most common route is Home→Highway 9→Skyline." Needs 10+ rides of data. Reserve insights JSONB on user profile for future AI-generated ride patterns.

6. Proposed Data Model

New tables required for this feature. Follows existing conventions: snake_case columns, UUID PKs, RLS policies, soft deletes, auto-updating updated_at.

rides

CREATE TABLE public.rides ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), user_id UUID NOT NULL REFERENCES public.users(id) ON DELETE CASCADE, motorcycle_id UUID REFERENCES public.motorcycles(id) ON DELETE SET NULL, status TEXT NOT NULL DEFAULT 'recording' CHECK (status IN ('recording','paused','completed','discarded')), started_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), ended_at TIMESTAMPTZ, paused_duration INTERVAL DEFAULT '0'::INTERVAL, distance_m INT, -- total distance in meters max_speed_mps REAL, -- max speed in m/s avg_speed_mps REAL, -- avg speed in m/s (excludes paused) elevation_gain REAL, -- meters gained elevation_loss REAL, -- meters lost route_polyline TEXT, -- encoded polyline for map display gps_quality REAL, -- % of waypoints with accuracy < 50m mileage_applied BOOLEAN DEFAULT false, -- whether odometer was updated safety_enabled BOOLEAN DEFAULT false, is_public BOOLEAN DEFAULT false, -- P2: for route sharing region TEXT, -- P2: geo region for discovery weather_snapshot JSONB, -- P2: start/end weather metadata JSONB DEFAULT '{}', -- extensibility created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), deleted_at TIMESTAMPTZ -- soft delete ); CREATE INDEX idx_rides_user ON rides(user_id); CREATE INDEX idx_rides_motorcycle ON rides(motorcycle_id); CREATE INDEX idx_rides_status ON rides(status); CREATE INDEX idx_rides_started ON rides(started_at DESC);

ride_waypoints

CREATE TABLE public.ride_waypoints ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), ride_id UUID NOT NULL REFERENCES public.rides(id) ON DELETE CASCADE, latitude DOUBLE PRECISION NOT NULL, longitude DOUBLE PRECISION NOT NULL, altitude REAL, -- meters above sea level speed_mps REAL, -- instantaneous speed in m/s accuracy REAL, -- horizontal accuracy in meters recorded_at TIMESTAMPTZ NOT NULL -- GPS timestamp ); CREATE INDEX idx_waypoints_ride ON ride_waypoints(ride_id); CREATE INDEX idx_waypoints_time ON ride_waypoints(ride_id, recorded_at);

Waypoints are uploaded in batches (every 50 points or on ride end). For a 1-hour ride at 5s intervals, this generates ~720 rows. At 60 bytes/row, a 1-hour ride stores ~43KB of waypoint data.

Note: safety_contacts and safety_events tables have been descoped from v1. The rides.safety_enabled column is reserved for future use.

9. Open Questions

Engineering Blocking

expo-location vs. react-native-background-geolocation. expo-location is simpler but may have reliability issues on Android 15 with aggressive battery optimization. react-native-background-geolocation by Transistor Software ($299/year license) uses motion-detection APIs and is battle-tested for ride/fitness apps. Recommend a 2-day spike to test both on physical devices (Android + iOS) with screen locked for 60+ minutes.

Engineering Blocking

Waypoint storage strategy. Storing every GPS point (720/hour at 5s intervals) works for individual rides but may become expensive at scale. Options: (a) Store all waypoints, query with pagination. (b) Store raw on device, upload only the encoded polyline + aggregate stats to the server. (c) Store all initially, add a background job to compress to polyline after 30 days. Recommendation: (b) for v1 — upload stats + polyline only, keep raw waypoints on device for detail view.

Engineering Blocking

Lean angle sensor reliability across devices. DeviceMotion gyroscope quality varies significantly between phone models. Some budget Android phones lack a gyroscope entirely. Recommend a 2-day spike to test lean angle accuracy on 5+ devices (iPhone 14+, Pixel 7+, Samsung S23+, budget Android). Define the minimum gyroscope sampling rate (target: 60Hz) and fallback behavior (hide gauge if unavailable).

Product Non-blocking

Free tier ride limit. Proposed: 5 rides/month free, unlimited Pro. Alternative: unlimited rides free, gate safety contact + history + maps behind Pro. The second approach maximizes adoption but reduces the Pro conversion lever. Recommendation: unlimited rides free (maximizes DAU), gate safety contact + full history + route maps + ride export behind Pro.

Design Non-blocking

Navigation placement. Options: (a) New 6th tab "Rides" — but 6 tabs is crowded on mobile. (b) Replace the current Home tab with a "Ride + Home" combined screen where the ride CTA is prominent. (c) Add ride logging inside the existing Garage tab. Recommendation: (b) — the home dashboard becomes ride-centric with "Start Ride" as the hero action, maintenance alerts and quick actions below.

Design Non-blocking

Ride HUD information density vs. glanceability. The prototype shows speed (hero), lean angle (left), altitude (right), and a stats row of 4 pills. For riders who don't mount their phone (phone in pocket), this HUD is invisible — the value is in post-ride stats only. Should we offer a "minimal HUD" mode (speed + duration only) for mounted riders, and a "pocket mode" (no HUD, just GPS + audio announcements) for unmounted riders?

Product Non-blocking

Unit conversion strategy. GPS data is in meters/m/s. The app stores distance_m and speed_mps internally. Display conversion happens at the UI layer using motorcycle.mileage_unit ('mi' or 'km'). For "Quick Ride" (no bike associated), default to the user's locale or last-used unit. Confirm this approach.

11. Architecture Notes

NestJS Module Structure

Following existing conventions in the codebase:

apps/api/src/modules/ ├── rides/ │ ├── rides.module.ts │ ├── rides.service.ts # CRUD, stats aggregation, polyline encoding │ ├── rides.resolver.ts # startRide, endRide, pauseRide, resumeRide, myRides, rideStats │ ├── models/ │ │ ├── ride.model.ts # @ObjectType() — mirrors rides table │ │ ├── ride-summary.model.ts # Aggregated stats for bike detail card │ │ └── ride-hud-data.model.ts # Live HUD response (if server-side aggregation needed) │ └── dto/ │ ├── start-ride.input.ts # motorcycleId (optional for Quick Ride) │ ├── end-ride.input.ts # distance_m, polyline, stats, max_lean_angle │ └── upload-waypoints.input.ts # Batch waypoint upload

Mobile Ride State Machine

IDLE → [Start Ride] → RECORDING → [Pause] → PAUSED → [Resume] → RECORDING ↓ ↓ [End Ride] [End Ride] ↓ ↓ SUMMARY ← ← ← ← ← ← ← ← ← ← ← ← SUMMARY ↓ [Accept Mileage / Skip] → SAVED → IDLE State persisted in expo-secure-store: { rideId, motorcycleId, status, startedAt, pausedAt, waypointBuffer[] }

Waypoint Upload Strategy

To minimize battery and network usage:

GPS points are buffered in memory (and periodically flushed to secure-store for crash recovery). Every 50 points or every 5 minutes (whichever comes first), the buffer is uploaded to the API as a batch mutation. On ride end, remaining points are flushed. The API computes the encoded polyline server-side from all waypoints and stores it on the rides.route_polyline column. This means the map can render from the compact polyline without re-fetching waypoints.

Mileage Unit Conversion

All internal storage is metric (meters, m/s). Conversion to user's preference (motorcycle.mileage_unit) happens at the GraphQL model layer via computed fields, or in the mobile UI layer. The distance_m column stores raw GPS distance. The summary screen converts: distance_m / 1609.344 for miles, distance_m / 1000 for km.
