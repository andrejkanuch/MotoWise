1. Problem Statement
Motorcycle riders use REVER (millions of downloads), Calimoto, and Scenic as daily ride-tracking companions — apps they open every time they ride. MotoVault, by contrast, is opened only when something needs attention: a diagnostic, a maintenance task, or an expense to log. The current DAU/MAU ratio is estimated at ~10%, a pattern typical of utility-only apps. Without a daily engagement touchpoint, MotoVault cannot build the habitual usage necessary for long-term retention or sustainable subscription revenue.
Who experiences this: Every active MotoVault user who rides regularly (estimated 70%+ of user base, riding 2–5 times per week in season). These riders currently have no reason to open MotoVault on a ride day.
Cost of not solving it: REVER and Calimoto own the “daily ride” moment. Every ride logged in REVER is a ride NOT logged in MotoVault. MotoVault’s maintenance schedules depend on accurate mileage, but motorcycle.current_mileage is only updated manually. Ride logging would auto-increment mileage, making OEM task thresholds significantly more accurate.
MotoVault’s unique advantage: No ride-tracking app auto-updates a bike’s service mileage or triggers maintenance reminders based on ride distance. REVER tracks rides. MotoVault can track rides AND tell you “you’re 200 miles from your next oil change” when you finish. This is the moat: ride → mileage → maintenance → expenses → AI diagnostics.
2. Goals
USER GOAL
Record every ride with zero friction. Starting a ride takes one tap from the home screen. Ending a ride presents instant stats (distance, duration, avg speed) and a mileage update prompt. Target: ride start-to-recording in under 3 seconds.

USER GOAL
Experience a real-time Ride HUD. While riding, the user sees a live map with their route, current speed (96pt, dominant), altitude, and ride stats — all on a dark, high-contrast screen optimized for outdoor visibility with glove-friendly 64pt touch targets.

USER GOAL
Keep maintenance schedules accurate without manual effort. Ride distance is added to the bike’s odometer after each ride. Maintenance tasks with target_mileage are automatically rechecked. Target: 85% of rides result in accepted mileage updates.

BUSINESS GOAL
Increase DAU/MAU from ~10% to 25%+. Ride logging creates a reason to open MotoVault on every ride. Measured at 90 days post-launch.

BUSINESS GOAL
Grow Pro subscriptions through high-frequency feature gating. Free tier: last 10 rides visible, unlimited recording. Pro: full history, GPX export, waypoint playback, route maps. Measured via incremental Free→Pro conversion.
3. Non-Goals (Explicit Scope Boundaries)
Turn-by-turn navigation. Navigation is Calimoto’s core offering, requiring deep map engine integration, voice guidance, and offline routing. MotoVault records rides — it doesn’t plan them.
Lean angle tracking in v1 (deferred to v1.1). Architecture review found high device variance, calibration UX complexity, and questionable gyroscope reliability on budget Android phones. The DB schema includes max_lean_angle as nullable for zero-migration-cost addition later. Not the differentiator — mileage sync is.
Community route discovery or social feed. Sharing and discovering routes requires a community layer, moderation, and network effects. Design the schema with is_public and region columns for future sharing, but don’t build the community UI.
Crash detection and automatic emergency calls. Requires accelerometer analysis, false-positive handling, and emergency service integration. Carries legal liability and needs dedicated safety engineering.
Safety contact / emergency SMS notifications. Requires Twilio/SNS backend, per-message costs, and liability review. Descoped from v1 — revisit once ride logging adoption is validated.
Group ride coordination or multi-rider tracking. Requires real-time multi-user location sharing with presence channels and privacy controls. Out of scope.

Frontend Scope Note
v1 targets basic, functional UX/UI — clean layouts, correct data flow, and reliable state management. Polished animations, advanced map interactions, and premium visual refinements are deferred to a follow-up frontend pass. The HUD design reference (Ride-HUD-Design.html) serves as the visual north star, but pixel-perfect implementation is not a v1 gate. Ship working, then ship beautiful.

4. User Stories
Core: Ride Recording
As a recreational rider, I want to tap one button (the center FAB in the tab bar, visible on every screen) to start recording my ride so that I can track distance and duration without fiddling with settings.
Edge: If no motorcycle is selected, prompt to add a bike or select “Quick Ride” without a bike association.

As a rider mid-ride, I want the app to continue recording my GPS track even when the screen is off or I switch to another app so that I get a complete route without keeping MotoVault in the foreground.
Edge: Battery saver mode may throttle GPS. Show a warning if low-power mode is detected.

As a rider finishing a ride, I want to see an instant summary (distance, duration, avg speed, max speed, elevation gain) and be prompted to update my bike’s mileage so that my maintenance schedule stays accurate.
Edge: If GPS accuracy was poor (>50% of waypoints with accuracy >100m), show a warning and present suggested mileage as editable.

As a touring rider on a multi-day trip, I want to pause and resume a ride (e.g., at a fuel stop or overnight) so that rest periods don’t count toward ride duration.
Edge: If the app is force-killed during a paused ride, the ride should be recoverable on next app open via MMKV-persisted state.

Core: Live Ride HUD
As a rider with a phone mounted on handlebars, I want to see a dark, high-contrast Ride HUD with my current speed displayed at 96pt so I can read it at a glance without taking my eyes off the road.
Edge: Speed must be readable in direct sunlight. White-on-black text. All controls must be 64pt minimum for gloved hands.

As a touring rider, I want to see my route drawn on a live map in real time so that I can see where I’ve been and orient myself geographically.
Edge: Map should auto-pan to keep current position centered. Show GPS quality indicator (green/yellow/red).

As a mountain/ADV rider, I want to see my current altitude and elevation changes so that I can track how much climbing I’ve done on a ride.
Edge: GPS altitude can be inaccurate (±30m). Display as integer, prefer barometric altitude if available.

As a commuter stuck in traffic, I want the app to automatically distinguish between moving time and stopped time so my average speed reflects actual riding, not time spent at red lights.
Edge: Auto-pause engages when speed=0 for 60 continuous seconds. Does not stop GPS — excludes from moving time calculation.

As a night rider, I want a night mode HUD that uses red-tinted UI so my night vision isn’t destroyed by a bright screen.
Edge: The app must never force max brightness. Respect system auto-brightness. Night mode toggle accessible from HUD.

Core: Mileage Sync
As a maintenance-conscious rider, I want my ride distance to be automatically suggested as a mileage update so that my OEM maintenance schedules stay accurate without manual editing.
Edge: Display as “Add X mi to odometer? (Current: Y mi → New: Z mi)” — never auto-commit.

As a rider who just hit a maintenance milestone, I want to see a notification after my ride saying “Oil change due” so that I act on maintenance tasks at the right time.
Edge: Only show for tasks with target_mileage that the new odometer reading exceeds.

Edge Cases & Empty States
As a new user who hasn’t added a bike yet, I want to start a “Quick Ride” (unassociated with a motorcycle) so I can try ride logging immediately.

As a rider in an area with poor cell service, I want ride recording to work fully offline (GPS only, no network required) and sync data when connectivity returns.
Edge: Client generates rideId (UUID) locally. All waypoint batches reference this ID. Sync queue processes on reconnect.

As a Free tier user, I want to see my last 10 rides and when I want more history, a clear upgrade prompt.
Edge: Free: unlimited recording, last 10 rides visible. Pro: full history, GPX export, waypoint playback.

6. Proposed Data Model (Post-Architecture Review)
All schema changes reflect architecture review findings. Key differences from v1.0 PRD: composite PK on ride_waypoints (H16), INT paused_duration_s (H18), auto_paused_duration_s (H17), client-supplied started_at with no DEFAULT (H14), public.update_updated_at() trigger (H7), RLS on both tables using public.is_admin() (H8, C2), and ride name column (Product Owner).

rides table
id UUID PK, user_id UUID FK, motorcycle_id UUID FK (nullable), name TEXT (nullable), status TEXT CHECK, started_at TIMESTAMPTZ NOT NULL (no default — client-supplied), ended_at TIMESTAMPTZ, paused_duration_s INT DEFAULT 0, auto_paused_duration_s INT DEFAULT 0, distance_m INT, max_speed_mps REAL, avg_speed_mps REAL, max_lean_angle REAL (v1.1), elevation_gain REAL, elevation_loss REAL, route_polyline TEXT, gps_quality REAL, mileage_applied BOOLEAN, is_public BOOLEAN, region TEXT, weather_snapshot JSONB, metadata JSONB, created_at, updated_at, deleted_at. Indexes: composite (user_id, motorcycle_id, started_at DESC WHERE deleted_at IS NULL), partial status index for active rides. Trigger: public.update_updated_at(). RLS: owner read/write, admin via public.is_admin().

ride_waypoints table
Composite PK: (ride_id UUID FK, recorded_at TIMESTAMPTZ). Columns: latitude DOUBLE PRECISION, longitude DOUBLE PRECISION, altitude REAL, speed_mps REAL, heading REAL, lean_angle REAL (v1.1), accuracy REAL. No separate id column — eliminates UUID B-tree write amplification. PK provides natural ordering. RLS via EXISTS subquery to rides table for ownership verification. Max 10,000 waypoints per ride (server-enforced).

GDPR Compliance (H15)
Scheduled purge: 30 days after soft-delete, permanently delete ride_waypoints and null out route_polyline on rides. Anonymization preserves aggregate stats (distance, duration) while removing PII (GPS coordinates). Future: /account/delete-data endpoint for user-initiated data erasure.

Product Strategy Note
The real moat is the closed loop: ride → mileage → maintenance → expenses → AI diagnostics. No competitor does this. Every design decision should reinforce this loop. Lean angle tracking, while impressive, is not the differentiator — mileage sync is.
