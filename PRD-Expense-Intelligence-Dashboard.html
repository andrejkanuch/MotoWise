1. Problem Statement

MotoVault captures detailed expense data across four categories (fuel, maintenance, parts, gear) per motorcycle, per date — including auto-generated expenses from completed maintenance tasks with cost breakdowns (parts, labor, total). Yet the mobile app presents this as a flat, chronological list filtered by bike and year, via a single expenses(motorcycleId, year) query that returns ytdTotal and categories[{category, total, expenses[]}]. There are no charts, no trends, no cost-per-mile calculations, no multi-bike comparison, and no exportable summaries.

Who experiences this: Every MotoVault user who logs expenses or completes maintenance tasks with costs — estimated at 60–70% of active users. Multi-bike owners (20–30% of the user base) are disproportionately affected because they have no way to compare cost of ownership across bikes.

Cost of not solving it: Users who can't visualize their spending don't see ongoing value from expense tracking, leading to logging fatigue and eventual churn. Competitors like MotorManage (600+ brands, offline-first) position documented service history as a resale value driver — without visual intelligence, MotoVault's expense data feels like bookkeeping rather than a strategic asset. Additionally, the existing Share Link feature (share_links table, 30-day expiring tokens) lacks a cost summary, reducing its effectiveness for private sales.

2. Goals

  • User Goal
    Understand spending patterns at a glance. Within 5 seconds of opening the dashboard, a user can see their total spend YTD, top expense category, and cost-per-mile for their selected motorcycle. Measured by: time-to-first-interaction analytics on the dashboard screen.
  • User Goal
    Compare cost of ownership across bikes. Multi-bike owners can view a side-by-side comparison of total cost, cost-per-mile, and category breakdown for all their motorcycles. Measured by: % of multi-bike users who view the comparison screen within 30 days.
  • User Goal
    Share financial proof when selling. Sellers can generate and share a clean, branded expense summary (via enhanced Share Link or PDF export) that proves maintenance investment to prospective buyers. Measured by: share/export actions per month.
  • Business Goal
    Increase Pro conversion by 8% via PDF export gating. The core dashboard is free; PDF export and smart alerts are Pro-only. Measured by: Free-to-Pro conversion rate delta within 60 days of launch.
  • Business Goal
    Increase expense logging frequency by 30%. Visual feedback loops ("you've logged X this month") motivate continued data entry. Measured by: average expenses logged per user per month, pre vs. post launch.

3. Non-Goals

Multi-currency support or currency conversion.
The maintenance_tasks table has a currency field (VARCHAR(3), default 'USD'), but expenses does not track currency independently. Adding conversion rates and multi-currency aggregation is a separate data model change. All v1 visuals assume a single currency per user.
AI-powered spending forecasts.
Predicting future costs based on riding patterns and maintenance schedules requires historical baselines and model training. This is a P2 future consideration — we design the data layer to support it, but don't build the prediction engine in v1.
Receipt scanning or OCR.
Autosist and similar apps offer receipt scanning. This requires camera integration, OCR processing, and field extraction — a separate feature initiative. Expenses continue to be logged manually or auto-created from maintenance task completion.
Budget setting or spending limits.
While natural for a financial dashboard, budget management adds significant UI complexity (setting budgets per category, per bike, per period) and notification logic. Better as a v2 follow-up once we validate that users engage with the base dashboard.
Integration with bank accounts or financial apps.
Plaid/bank integration is a separate compliance and security initiative. Out of scope for an expense visualization feature.

4. User Stories

Primary Persona: Single-Bike Owner

As a budget-conscious rider, I want to see a visual breakdown of my spending by category (fuel, maintenance, parts, gear) so that I know where my money is going.

As a daily commuter, I want to see my cost-per-mile (or cost-per-km) based on my total spend and current mileage so that I can compare my motorcycle's running cost to alternatives.

Edge case: If currentMileage is null or 0, display "Log your mileage to see cost-per-mile" with a link to edit the bike's mileage.

As a seasonal rider, I want to see monthly spend trends over the past 12 months so that I can understand how my costs fluctuate across riding season vs. winter storage.

Edge case: Months with $0 spending should show as zero-height bars, not be omitted from the chart.

Primary Persona: Multi-Bike Owner

As a multi-bike owner, I want to compare total cost of ownership across all my motorcycles in a single view so that I can make informed decisions about which bikes to keep, sell, or ride more.

Edge case: Deleted (soft-deleted) bikes should not appear. Bikes with zero expenses should show as $0, not be hidden.

As a multi-bike owner, I want to switch between per-bike dashboard and all-bikes comparison without losing my selected time period so that I can drill down naturally.

Primary Persona: Seller / Buyer

As a rider preparing to sell, I want to generate a clean PDF expense report for my motorcycle — showing total investment, category breakdown, and maintenance timeline — so that I can share it with prospective buyers as proof of care.

Edge case: If the bike has zero expenses, the export should still generate with "No expenses recorded" rather than failing.

As a buyer viewing a shared link, I want to see an expense summary on the public share page so that I can evaluate the seller's investment in the bike without needing a MotoVault account.

Edge Cases & Empty States

As a new user with no expenses logged, I want to see an encouraging empty state on the dashboard that explains what insights I'll unlock by logging my first expense, with a clear CTA to "Log Your First Expense."

As a user who only has auto-generated maintenance expenses, I want the dashboard to still render correctly and suggest logging fuel and gear expenses for a complete picture.

As a Pro subscriber, I want to receive smart alerts when my spending patterns change significantly (e.g., "Fuel costs up 40% this quarter" or "This bike costs $0.32/mi vs $0.18/mi for your other one") so that I take action without manually monitoring numbers.

Alerts should only fire when there are at least 3 months of data to establish a baseline. Never alert on the first month.

P2 Future Considerations

FeatureDesign Consideration for v1
AI Spending Forecast Predict annual costs based on riding patterns, OEM schedule, and historical data. For v1: ensure the new expenseDashboard query returns monthly aggregates with enough granularity (per-category, per-month) to feed a future ML model. Store aggregated snapshots if needed for trend analysis.
Budget Setting & Alerts Allow users to set monthly/annual budgets per category or per bike. For v1: the summary cards already show total spend — a future "budget bar" can overlay on top without restructuring the UI. No schema changes needed now.
Insurance/Registration Categories The current category CHECK constraint is ('fuel', 'maintenance', 'parts', 'gear'). Riders also track insurance, registration, loan payments, and parking. For v1: do NOT expand categories yet — validate demand first. The DB migration to add enum values is trivial when needed.
Depreciation Tracking Track bike purchase price and compare against estimated current value. For v1: the motorcycles table does not have a purchase_price column — consider adding it as a nullable DECIMAL in a future migration. The Bike Passport (separate PRD) is the better home for this feature.

Measurement Plan

All metrics will be evaluated at three checkpoints: 1 week (sanity check — are charts rendering, are users finding the feature?), 30 days (leading indicators), and 90 days (lagging indicators + decision on P1 investment). Dashboard adoption below 40% at 30 days triggers a UX review and discoverability investigation before proceeding with P1 features.

7. Open Questions

Engineering Blocking

Client-side vs. server-side aggregation for charts. The current expenses(motorcycleId, year) query returns individual expense records grouped by category. For a 12-month trend chart, should we compute monthly buckets client-side (simpler, works now) or add a new expenseDashboard resolver with pre-aggregated monthly totals (better performance, cleaner API)? Recommendation: start with client-side; add server aggregation if p95 load time exceeds 3s for users with 100+ expenses.

Engineering Blocking

Charting library for React Native. Options: (a) react-native-chart-kit (simple but limited customization), (b) victory-native (powerful but heavier), (c) react-native-skia + custom drawing (maximum control, most effort). Which aligns with existing dependencies and the design system?

Design Non-blocking

Dashboard entry point. Where does the Expense Dashboard live in the navigation? Options: (a) new tab within the Garage bike detail screen, (b) dedicated screen accessible from home dashboard quick actions, (c) floating action button on the existing expense list. Recommendation: (a) tab within bike detail — aligns with the per-bike mental model.

Design Non-blocking

Multi-bike comparison entry point. Should comparison be: (a) a separate screen accessible from the Garage tab header, (b) a toggle within the per-bike dashboard ("Switch to All Bikes"), or (c) a widget on the Home tab? Recommendation: (b) toggle within the dashboard for discoverability.

Product Non-blocking

Should maintenance task costs appear separately on the dashboard? Currently, completing a task with cost auto-creates an expense (category: 'maintenance'). The dashboard would show this as a maintenance expense. Should we also show a separate "Maintenance Cost" view that breaks down parts_cost vs. labor_cost from the maintenance_tasks table, or is the expense-level view sufficient?

Product Non-blocking

Mileage unit handling. motorcycle.mileageUnit can be 'mi' or 'km'. Cost-per-mile should respect the user's preference. Confirm: should we display as "Cost/mi" or "Cost/km" based on the bike's mileageUnit, or should there be a global user preference?

Phase 1: Core Dashboard (Weeks 1–2)

  • Summary cards (R1)
  • Category donut chart (R2)
  • Monthly trend bar chart (R3)
  • Time period selector (R4)
  • Recent expense list (R5)

Phase 2: Comparison + Export (Weeks 3–4)

  • Multi-bike comparison (R6)
  • PDF export — Pro gate (R7)
  • Enhanced share link (R9)
  • New expensesSummaryAll resolver

Ship if Phase 1 adoption > 40%.

Phase 3: Intelligence (Weeks 5–6)

  • Smart spending alerts (R8)
  • Notification preference integration
  • Alert scheduling logic (cron)
  • Year-over-year comparisons on cards

Ship if Pro conversion lifts from Phase 2.

Dependencies

No hard blockers. All data exists in the current schema. The expenses table, maintenance_tasks table, and motorcycles table have all required fields. The only new backend work is the optional expensesSummaryAll resolver (Phase 2) and alert scheduling (Phase 3). Phase 1 is entirely a mobile UI effort over the existing GraphQL API.

Existing GraphQL Query

expenses(motorcycleId: String!, year: Int) → ExpenseSummary { ytdTotal, categories[{ category, total, expenses[{ id, amount, category, description, date, createdAt }] }] }

This returns all data needed for Phase 1. Phase 2 requires a new expensesSummaryAll(year: Int) → [{ motorcycleId, motorcycleName, totalSpend, categories[{ category, total }] }] resolver.
