The Ride Logging + Live Ride HUD spans three discrete layers:

  • Mobile Client (Expo 55 / React Native 0.83): GPS via expo-location + expo-task-manager, sensors via expo-sensors DeviceMotion, maps via react-native-maps, state via Zustand + TanStack Query

  • Persistence (Supabase PostgreSQL): rides + ride_waypoints tables, RLS policies, triggers

Data Flow Summary

  1. Start Ride: Mobile creates local ride state, starts background GPS + DeviceMotion listeners
  2. GPS Updates: Background task fires every 5–20 meters, buffers waypoint data locally
  3. Sensor Fusion: DeviceMotion (60Hz) feeds lean angle, smoothed and downsampled for HUD display
  4. Aggregates: Client computes distance, speed, elevation incrementally on each GPS callback
  5. Periodic Flush: Every 50 waypoints, background sync uploads them to server
  6. End Ride: Client finalizes aggregates, encodes polyline, calls endRide mutation
  7. Mileage Sync: Post-ride prompt for user to accept/edit/skip mileage update
  8. Maintenance Check: After mileage update, check if maintenance tasks are due

RLS Policies

Row-level security ensures users only access their own rides. Apply the following policies to both tables:

🔐 Rides RLS Policies 
-- Policy 1: Users can read their own rides + admins can read all
CREATE POLICY "Enable read access for ride owner or admin"
  ON public.rides
  FOR SELECT
  USING (
    user_id = auth.uid()
    OR (
      SELECT role FROM public.users
      WHERE id = auth.uid()
    ) = 'admin'
  );

-- Policy 2: Users can insert their own rides
CREATE POLICY "Enable insert for authenticated users"
  ON public.rides
  FOR INSERT
  WITH CHECK (user_id = auth.uid());

-- Policy 3: Users can update their own rides
CREATE POLICY "Enable update for ride owner"
  ON public.rides
  FOR UPDATE
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

-- Policy 4: Users can delete (soft) their own rides
CREATE POLICY "Enable delete for ride owner"
  ON public.rides
  FOR DELETE
  USING (user_id = auth.uid());

6Sensor Fusion — Lean Angle Tracking

DeviceMotion integration, low-pass filtering, calibration flow, and 60Hz to 10Hz downsampling.

Lean Angle Service Implementation

⚖️ LeanAngleService 
import { DeviceMotion } from 'expo-sensors';

class LeanAngleService {
  private calibrationQuaternion: Quaternion | null = null;
  private lowPassAlpha = 0.15; // Smoothing factor
  private lastFilteredAngle = 0;

  async startTracking(onUpdate: (angle: number) => void) {
    const available = await DeviceMotion.isAvailableAsync();
    if (!available) return false;

    DeviceMotion.setUpdateInterval(16); // ~60Hz

    this.subscription = DeviceMotion.addListener((data) => {
      if (!data.rotation) return;

      const rawAngle = this.computeLeanAngle(data.rotation);
      const calibrated = this.applyCalibration(rawAngle);
      const filtered = this.lowPassFilter(calibrated);
      const clamped = Math.max(-45, Math.min(45, filtered));

      onUpdate(clamped);
    });

    return true;
  }

  private computeLeanAngle(rotation: { alpha, beta, gamma }): number {
    // gamma = rotation around the front-to-back axis (lean)
    // Convert from radians to degrees
    return (rotation.gamma * 180) / Math.PI;
  }

  private applyCalibration(rawAngle: number): number {
    if (!this.calibrationQuaternion) return rawAngle;
    return rawAngle - this.calibrationQuaternion.gammaOffset;
  }

  private lowPassFilter(value: number): number {
    this.lastFilteredAngle =
      this.lowPassAlpha * value + (1 - this.lowPassAlpha) * this.lastFilteredAngle;
    return this.lastFilteredAngle;
  }

  async calibrate(): Promise<void> {
    // Sample 30 readings over 500ms, average them as zero reference
    const samples: number[] = [];
    return new Promise((resolve) => {
      const sub = DeviceMotion.addListener((data) => {
        if (data.rotation) {
          samples.push((data.rotation.gamma * 180) / Math.PI);
          if (samples.length >= 30) {
            sub.remove();
            const avg = samples.reduce((a, b) => a + b) / samples.length;
            this.calibrationQuaternion = { gammaOffset: avg };
            persistToSecureStore(this.calibrationQuaternion);
            resolve();
          }
        }
      });
    });
  }
}

Performance Optimization: 60Hz → 10Hz Downsampling

  • Sensor reads at 60Hz (16ms intervals) for smooth filtering and accurate low-pass output
  • Low-pass filter (α=0.15) applied at each reading to reduce noise and jitter
  • Only emit to React state every 6th reading (~10Hz / 100ms) to reduce re-render frequency
  • Reduces React re-renders from 60/sec to 10/sec, lowering CPU usage during HUD display
  • Waypoint lean_angle stored at GPS frequency (every ~5 seconds) — take the max absolute lean in the interval
💡 Calibration Flow
  1. First ride → detect no calibration stored → show modal
  2. "Mount your phone on the handlebars, hold bike upright, tap Calibrate"
  3. 500ms sampling → average → store zero reference in expo-secure-store
  4. Re-calibrate accessible from settings anytime
  5. Fallback: if DeviceMotion unavailable → hide lean gauge, expand altitude display

7Waypoint Buffer & Upload Strategy

Client-side buffering, polyline encoding, and v1 strategy (stats-only upload with async waypoint sync).

Buffering Flow

GPS callback (every 5s/20m)
  │
  ▼
addWaypoint()
  ├── Push to in-memory waypoints[] array
  ├── Push {lat,lng} to routeCoordinates[] (for map polyline)
  ├── Update running aggregates (distance, max speed, elevation)
  ├── Update GPS quality counters
  │
  ├── waypoints.length >= 50?
  │     YES → flushWaypoints()
  │     │     ├── Clone buffer, clear array
  │     │     ├── Call uploadWaypoints mutation (fire-and-forget)
  │     │     └── On failure: re-add to buffer, retry on next flush
  │     NO → continue
  │
  └── persistState() every 10 waypoints (crash recovery)

v1 Strategy: Upload Polyline + Stats Only

To minimize payload size and enable fast ride completion, the v1 implementation follows this strategy:

  • Client computes ALL aggregates locally (distance, avg/max speed, elevation gain/loss)
  • Client encodes route as Google Encoded Polyline using @mapbox/polyline
  • On ride end: upload ONLY the polyline + aggregate stats via endRide mutation
  • Waypoints uploaded in background as a secondary operation (for Pro ride detail view)
  • This means endRide is fast (single mutation, <1KB payload) even on slow connections

Performance Considerations

  • Speed display: update at 1Hz (throttle GPS speed to 1s intervals for stable reading)

The lean angle gauge should use Reanimated v4's useSharedValue + useAnimatedStyle to animate the needle without triggering React re-renders. This keeps the gauge smooth at 60fps even when the ride state updates at lower frequencies.

10Offline-First Architecture

Design principle: rides work 100% offline. Network is only needed for sync.

Offline Workflow

OFFLINE FLOW:
1. Start ride → Create ride in local state only (no GraphQL call needed)
   - Generate UUID client-side for rideId
   - Store in Zustand + expo-secure-store

2. During ride → All GPS + sensor data stays local
   - Waypoints buffered in memory
   - Periodic persist to expo-secure-store (every 10 waypoints)

3. End ride → Compute all stats locally
   - Distance, speed, elevation — all from local waypoints
   - Encode polyline locally
   - Show summary screen immediately (no network needed)

4. Sync when online → Background sync queue
   - startRide mutation (creates server-side ride record)
   - endRide mutation (uploads stats + polyline)
   - uploadWaypoints mutation (background, chunked)
   - updateMotorcycle mutation (if mileage accepted)

   If sync fails → Queue in AsyncStorage, retry on next app open
   Show indicator: "Ride saved locally — will sync when connected"

✅ Crash Recovery Benefit

Because all ride data is persisted locally, even if the app crashes or the device loses power during a ride, the user can resume on next app open. The persisted state includes all waypoints up to the last flush, allowing accurate ride completion even if the final upload fails.

12Security Considerations

Privacy, data protection, and security best practices.

  • RLS policies on rides/ride_waypoints ensure users only access own data
  • Location data is sensitive PII — encrypt at rest (Supabase default), in transit (HTTPS)
  • Waypoint data never sent to third parties — stored only in Supabase
  • Background location permission rationale must be clear (App Store review requirement)
  • Rate limiting on uploadWaypoints: 100 waypoints/call, max 10 calls/minute per user
  • Validate all waypoint coordinates server-side (lat -90..90, lng -180..180)
  • JWT auth via GqlAuthGuard on all mutations (no anonymous ride logging)
  • Soft delete rides (set deleted_at timestamp) rather than hard delete to preserve audit trail
🔒 App Store Compliance

Apple requires clear explanation of why background location is needed. The permission request should explain "MotoVault tracks your location during rides to record your route, speed, and distance, even if the app is in the background." Include a screenshot of the ride HUD in your App Store submission.
